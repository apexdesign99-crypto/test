# AI社員 — 建築設計事務所向け

集客・営業・マーケティング・事務・BIM設計の 5 職種を AI社員として立ち上げ、
**事務所全体で 1 つの案件台帳を共有**しながら働かせるためのツールです。

集客が拾った反響を営業が追い、設計が図面を起こし、事務が請求する——という流れは、
全員が同じ案件を見られないと成立しません。この台帳が中心にあります。

思考エンジンは Claude Opus 5(`claude-opus-5`)です。

## まずは集客担当から

### 手順 1. 事務所プロフィールを設定する(最初にやる)

**これを飛ばすと、施主向けの文面がまともに書けません。** 対応エリアも料金も相談の流れも
AI は知らないからです。未設定のあいだ、社員はそれらを書かずに【要記入】の差し込み欄として
残すよう指示されています(作り話を防ぐための意図的な設計です)。

```bash
pip install -e .
export ANTHROPIC_API_KEY=sk-ant-...   # または `ant auth login`

python -m ai_employee office \
  --name "○○設計事務所" \
  --location "東京都世田谷区" \
  --areas "東京23区,川崎市,横浜市" \
  --specialties "木造戸建の新築,店舗改修" \
  --fee-policy "設計監理料は工事費の10%(最低300万円)" \
  --consultation-flow "お問い合わせ,初回相談(無料・約90分),現地調査,プラン提案,設計契約" \
  --business-hours "平日9:00-18:00" \
  --contact "03-0000-0000 / info@example.com"
```

`ai-office/_company/office.json` に保存されるので、後から直接編集しても構いません。
`python -m ai_employee office --show` で、社員に渡っている内容をそのまま確認できます。

### 手順 2. 集客担当を採用する

```bash
python -m ai_employee hire --id shukyaku --name "集客 AI" --template lead
```

### 手順 3. 反響を渡す

問い合わせ本文をそのまま貼り付けてください。案件化・初回返信の下書き・確認事項の洗い出しまで
一度に行います。

```bash
python -m ai_employee ask --id shukyaku \
  "Instagram のDMから問い合わせ。佐々木様、目黒区で戸建の新築を検討中とのこと。
   案件を起こして、初回返信の下書きを作って"
```

集客担当は次のように動きます。

1. `list_projects` で同じ施主からの再問い合わせでないか確認
2. `add_project` で起票(流入経路を必ず記録)
3. 初回返信の下書きを作成 — 御礼・相談内容の復唱・次の具体的な提案(日程候補・所要時間・
   オンライン可否)・当日確認したいこと・連絡先の 5 点が必ず入ります
4. `update_project` で次アクションと期限を設定
5. 書かれていなかった予算・時期・敷地の有無は「未確認」として確認事項に残します

### 手順 4. 週次で取りこぼしを潰す

集客で一番損が出るのは、反響そのものより**追客が止まった案件**です。

```bash
python -m ai_employee stale                  # 14日以上動いていない案件
python -m ai_employee stale --days 7
python -m ai_employee ask --id shukyaku "追客が止まっている案件を洗い出して、次の一手を提案して"
```

```
14 日以上動いていない案件 2 件(放置が長い順)
  [d14dc1c5] 田中様 世田谷区 新築  反響  最終更新 2026-07-27
      担当: shukyaku  経路: HP問い合わせ  次: 未設定
```

台帳を更新すれば追客対象から外れます(更新日 = 最終接触日として扱う設計です)。

### 手順 5. どの経路が効いているかを見る

```bash
python -m ai_employee sources
python -m ai_employee sources --since 2026-04-01
```

```
流入経路別の反響 (全期間)
  経路                 反響 進行中 受注 失注  受注率
  HP問い合わせ            3      2    0    1  0.0%  ※母数少
  Instagram               1      1    0    0  -
  紹介                    1      0    1    0  100.0%  ※母数少
```

受注率は決着済み(受注+失注)に対する割合で、進行中は母数に含みません。
決着が 5 件未満の経路には「母数少」が付き、集客担当もその場合は効果を断定しません。
まだ決着ゼロの経路は受注率 `0%` ではなく `-` と表示します(混同を避けるため)。

## 次は営業担当

集客が起票した案件をそのまま引き継ぎます。営業で損が出るのは**聞き漏れ**と**その場の概算**なので、
どちらも AI の自己申告に任せず、システム側で機械的に扱います。

### 聞き漏れをシステムが数える

初回相談で押さえる 10 項目を案件に構造化して持たせています。聞けた項目だけを記録し、
**渡さなかった項目は「未確認」のまま残ります**。推測で埋めることはできません
(項目名がスキーマ外なら弾かれ、空文字は記録されません)。

```bash
python -m ai_employee ask --id eigyo \
  "佐々木様の初回相談。予算は総額4500万円、土地は目黒区に所有、入居は2027年春希望。
   ヒアリング結果を記録して、次に確認すべきことを教えて"

python -m ai_employee hearing <案件ID>
```

```
[3e0ac3af] 佐々木様 目黒区 新築 のヒアリング状況

  聞けている項目
    予算(総額)                        総額4500万円(建物のみ)
    土地の状況(所有/取得済/検討中/未定) 所有(目黒区・約40坪)
    入居・開業の希望時期              2027年春

  提案前に必要な未確認項目 3 件
    ・資金計画(自己資金・借入)
    ・要望の優先順位
    ・決裁者

  → 必須項目が未確認です。提案より先に確認してください。
```

営業担当は**プラン提案・見積の話に入る前に必ず `hearing_gaps` を確認**し、
必須項目が欠けていれば提案を作らず、先に確認事項を提示します。

項目は `ai_employee/company.py` の `HEARING_ITEMS` で定義しています。
事務所の初回相談シートに合わせて増減させてください(第 3 要素が「提案前に必須か」です)。

### 概算は Python が計算する

**坪単価を AI に推測させません。** 事務所が設定した単価と料率を使い、計算は Python 側で行い、
社員には結果と算定根拠だけを渡します。

```bash
python -m ai_employee office \
  --unit-prices "戸建住宅:80-100,店舗:60-90" \
  --design-fee-rate 10 --design-fee-minimum 300

python -m ai_employee estimate --kind 戸建住宅 --tsubo 35
python -m ai_employee estimate --kind 戸建住宅 --sqm 115.7   # ㎡でも可
```

```
戸建住宅 延床 35.0 坪 (115.7 ㎡) の概算
  坪単価        80〜100 万円/坪
  工事費        2,800〜3,500 万円
  設計監理料    300〜350 万円  工事費の 10.0%(最低額 300 万円を適用)

  坪単価に基づく概算であり、確定金額ではない。地盤・外構・別途工事・設備グレードで変動する。
```

**単価が未設定の用途では算定が失敗します。** そのとき社員は概算金額を書かず、
算定できない旨と必要な設定を報告します。

```
「共同住宅」の坪単価が事務所プロフィールに未設定のため、概算を出せません。
```

設計監理料の最低額は、下回った側にだけ適用されます(35 坪なら 280 万円 → 300 万円)。
概算を提示するときは、算定根拠と「確定金額でないこと」「変動要因」を必ず併記させています。

## 次はマーケティング担当

この職種で一番のリスクは、**施主の許諾なく事例を公開すること**です。
そこで掲載許諾を案件の属性として持たせ、AI が推測できないようにしました。
表現チェックも、AI の「問題ないと思います」ではなく機械的なパターン照合で行います。

### 掲載許諾を案件が持つ

案件の許諾は既定で「未確認」から始まります。**確認しないと公開できない状態がスタート地点**です。

```bash
python -m ai_employee consent <案件ID> --status 条件付き \
  --conditions "施主名は伏せる。外観写真のみ。所在地は市区まで。"

python -m ai_employee consent <案件ID>     # 状態と発信履歴の確認
```

状態は 4 つです。

| 状態 | 社員の振る舞い |
| --- | --- |
| `未確認` | 原稿を書かない。代わりに施主への許諾確認の依頼文を用意する |
| `許諾済` | 事務所情報の範囲で発信してよい |
| `条件付き` | 記録された条件を原稿に必ず反映する |
| `不可` | **匿名化しても書かない** |

「条件付き」で条件を空にすることはできません。後から何が許されているのか分からなくなるためです。
**許諾のない案件は発信の記録すらできません** — 「許諾を取らずに出した」が記録上も成立しません。

### 発信ネタの棚卸し

```bash
python -m ai_employee candidates --channel Instagram
```

```
発信できる案件 2 件 (Instagram で未発信)
  [ab33e121] 田中邸 新築             条件付き
        条件: 施主名は伏せる。外観写真のみ。所在地は市区まで。
  [2fc58371] 佐藤ビル 改修           許諾済  既出: HP施工事例

先に施主の許諾が必要な案件 1 件
  [2a69ee15] 山本邸 平屋             未確認
  許諾が取れるまで、これらを題材にした原稿は書けません。
```

許諾があってまだ出していない案件が「書けるネタ」です。チャネル別に管理するので、
HP に出した事例をまだ Instagram に出していない、といった取りこぼしが拾えます。
「不可」の案件は候補にすら出ません。

### 表現チェック

社外に出る原稿を、決まったパターンで機械的に照合します。

```bash
python -m ai_employee check --file 下書き.md
python -m ai_employee check --text "地域No.1の設計事務所です"
```

```
確認が要る箇所 8 件
  L3 [最上級表現] No.1
      # 光を通す木造の家  弊社は地域〈No.1〉の設計事務所です。田中様邸は世田谷区2丁
      客観的な裏付けと出典がなければ使えない。順位を示す調査名・時点・範囲を添えるか、削除する。
  L3 [個人が特定される情報] 田中様邸
      施主が特定されうる。掲載許諾の条件を確認し、必要なら「S様邸」等に伏せる。
  L4 [裏付けが要る数値] 200件以上
      実績の件数は、案件台帳や社内記録で裏が取れたものだけ使う。取れないなら削除する。
```

拾うのは、最上級表現・唯一性の主張・断定と保証・完全性の主張・比較優位の主張・
個人が特定される情報・裏付けが要る数値です。匿名化済みの「S様邸」や日付の「2027年春」は
拾いません。マーケ担当は原稿を提示する前に必ずこれを通し、指摘を直すか理由を書きます。

> **これは適法性の判断ではありません。** 拾えるのは既知のパターンだけで、見落としも誤検出もあります。
> 社員にも「チェックを通ったことを『問題なし』と報告するな」と指示していますが、
> 最終的な掲載可否は必ず人が判断してください。
>
> パターンは `ai_employee/copycheck.py` の `_RULES` にあります。御社で気になる表現を足せます。

## 次は事務担当

設計事務所の請求は**出来高払い**でステージと連動します。事務の実害はほぼ
「請求漏れ」と「入金遅延」の 2 つに集中するので、どちらも機械的に検出します。
金額の計算も、ここでも Python 側で行います。

### 出来高払いの配分を設定する

```bash
python -m ai_employee office \
  --billing-schedule "契約金:30:設計契約,基本設計完了:30:基本設計,実施設計完了:30:実施設計,引渡:10:竣工" \
  --tax-rate 10 --payment-term-days 30
```

`表示名:配分%:請求できるステージ` の形式です。**合計が 100% でないと設定できません。**
未設定のあいだ、社員は請求計画を作れません(事務所の契約実態を推測させないため)。

消費税率も未設定なら税込を算出しません。設定値は「事務所の設定値であり、
適用税率は事務所で確認するもの」として社員に渡されます。

### 契約したら請求計画を作る

```bash
python -m ai_employee billing --project <案件ID> --setup 1000001    # 契約金額(円・税別)
```

```
[6aa19c28] 田中邸 新築  実施設計
  契約金額: 1,000,001 円 (税別)

  m1  契約金                 300,000  入金済  請求 2026-08-27  入金 2026-08-27
  m2  基本設計完了           300,000  請求済  請求 2026-08-27
  m3  実施設計完了           300,000  未請求
  m4  引渡                   100,001  未請求
        端数 1 円を調整

  入金済 300,000 / 未入金 300,000 / 未請求 400,001 円
```

割り付けは Python が計算し、**円未満の端数は最終回に寄せて合計を契約金額に必ず一致させます**。
1 円でもずれると請求書が合わなくなるためです。

請求書を出したら請求済に、入金を確認したら入金済にします。

```bash
python -m ai_employee billing --project <案件ID> --invoiced m3
python -m ai_employee billing --project <案件ID> --paid m2
```

**請求済・入金済の実績がある案件は、請求計画を作り直せません。** 実績が消えるためです
(金額の変更が必要なら個別の回を直します)。

### 請求漏れと入金遅延を洗い出す

```bash
python -m ai_employee billing --alerts
```

```
請求漏れの疑い 2 件 (計 2,270,367 円)
  [6aa19c28] 田中邸 新築         実施設計完了    1,370,367 円
      案件は「実施設計」まで進んでいるが、「実施設計」到達で請求できる回が未請求。
  [80b77b1a] 佐藤ビル 改修       基本設計完了      900,000 円
      案件は「基本設計」まで進んでいるが、「基本設計」到達で請求できる回が未請求。
```

**請求漏れ**は、案件のステージが請求条件のステージに達しているのに未請求の回です。
BIM 担当がステージを進めれば、事務が何もしなくても翌日には検出されます。
**入金遅延**は、請求済のまま支払期日を過ぎた回です。失注案件は対象外です。

```bash

```

```

  案件                              契約額        入金済        未入金        未請求
  田中邸 新築                    4,567,890     1,370,367     1,370,367     1,827,156
  佐藤ビル 改修                  3,000,000             0       900,000     2,100,000
  ----------------------------------------------------------------------------------
```

事務担当には「金額を暗算しない」「報告前に必ず `billing_alerts` を確認する」
「入金済にするのは通帳や入金記録で裏が取れたときだけ(施主の『振り込んだ』という伝聞では記録しない)」
を行動指針として明記しています。

> 提出書類の要否・様式・期限については、所管行政庁の最新の案内で確認するよう指示しており、
> 記憶や一般論で断定させません。法定様式の判断は必ず人が確認してください。

## 案件台帳

事務所で 1 つだけ持つ共有台帳です(`ai-office/_company/projects.json`)。
全社員がここを読み書きするので、部署をまたいだ引き継ぎが記録として残ります。

**ステージ**: 反響 → 初回相談 → 現地調査 → プラン提案 → 見積 → 設計契約 →
基本設計 → 実施設計 → 確認申請 → 着工 → 監理 → 竣工 → アフター

**ステータス**: `active` 進行中 / `won` 受注 / `lost` 失注 / `onhold` 保留 / `done` 完了

案件の更新には必ず理由(`note`)が要ります。誰がいつ何をなぜ変えたかが履歴に差分つきで残るため、
「この案件、前回どこまで話したか」を後から追えます。

```bash
python -m ai_employee projects --stage 実施設計   # ステージで絞る
python -m ai_employee projects --owner bim        # 担当で絞る
python -m ai_employee projects --query 世田谷     # 案件名・顧客名・計画地で検索
python -m ai_employee project <案件ID>            # 1 件の詳細と全経緯
```

ステージ・用途種別は `ai_employee/company.py` の `STAGES` / `KINDS` を編集すれば変えられます。

## 社員が使えるツール

| ツール | 用途 |
| --- | --- |
| `add_project` / `list_projects` / `get_project` | 案件の起票・検索・経緯の確認 |
| `update_project` / `log_project` | 案件の更新と履歴追記(理由の記載が必須) |
| `pipeline` | ステージ別の進行中件数(営業会議の材料) |
| `stale_projects` | 一定期間動いていない案件(追客漏れの検知) |
| `source_report` | 流入経路別の反響数・受注率 |
| `record_hearing` / `hearing_gaps` | ヒアリングの記録と、未確認項目の検出 |
| `estimate_cost` | 工事費・設計監理料の概算算定(計算は Python 側) |
| `publication_status` / `record_consent` | 掲載許諾の確認と記録 |
| `publication_candidates` / `log_publication` | 発信ネタの棚卸しと発信記録 |
| `review_copy` | 原稿の表現チェック |
| `setup_billing` / `update_billing` | 出来高払いの請求計画と、請求・入金の記録 |
| `billing_status` / `billing_overview` | 案件別・全社の請求状況 |
| `billing_alerts` | 請求漏れと入金遅延の検出 |
| `tax_breakdown` | 消費税の計算(税率未設定なら算出しない) |
| `record_note` / `search_notes` | 業務メモ。`project_id` で案件に紐付く |
| `add_task` / `list_tasks` / `complete_task` | 自分のタスク管理 |
| `list_files` / `read_file` / `write_file` | 成果物の読み書き |
| `current_datetime` | 現在日時・曜日 |
| `web_search` | Web 検索(マーケ担当と `--web` 付きで採用した社員のみ) |

`profile.json` の `tools` に列挙された名前だけが有効です。書かれていないツールはモデルに提示すら
されないため、権限の付与・剥奪はこのファイルで完結します。

ファイル操作は `ai-office/<社員ID>/files/` の中に閉じ込められています。
`..` やシンボリックリンクによるワークスペース外へのアクセスは拒否されます。

## この AI社員がやらないこと

事務所の業務では、AI が知ったかぶりをすると実害が出ます。各職種の行動指針で以下を禁じています。

- **法規を記憶で断定しない**(BIM設計・事務)。建築基準法・条例・省エネ基準の適合判断や
  提出書類の要否は、法令原文と所管行政庁で確認するよう指示し、判断が要る箇所は「要確認」と
  明示させます。
- **モデルを見ずに図面を推測しない**(BIM設計)。Revit / Archicad を直接操作できないことを
  自認させ、指示は担当者がそのまま実行できる手順として書かせます。
- **未確認の数字を書かない**(営業・事務)。予算・面積・工期は「聞けた事実」と「未確認」を
  必ず区別させます。金額は `estimate_cost` / `billing_*` でのみ算定させ、暗算を禁じています。
  聞き漏れも請求漏れも、AI の自己申告ではなく台帳の状態から機械的に検出します。
- **伝聞で入金済にしない**(事務)。通帳や入金記録で裏が取れたときだけ記録させます。
- **事務所情報を作らない**(全職種)。事務所プロフィールが未設定なら、施主向けの文面に
  事務所名・エリア・料金・日程を書かず、【要記入】の差し込み欄として残します。
- **許諾のない案件を題材にしない**(マーケ)。掲載許諾は案件の属性として持ち、既定は「未確認」。
  未確認・不可の案件は匿名化しても原稿を書かせず、発信の記録もできません。
  原稿は提示前に `review_copy` を通し、最上級表現・個人情報・裏付けのない数値を洗います。

これらはプロンプト上の制約であり、出力の確認を不要にするものではありません。
対外的な文書と法規判断は、必ず人が確認してから使ってください。

## ワークスペースの中身

```
ai-office/
├── _company/
│   ├── office.json      事務所プロフィール(施主向け文面の前提)
│   └── projects.json    案件台帳(事務所で共有)
└── <社員ID>/
    ├── profile.json     職務定義書(人間が編集する)
    ├── notes.jsonl      業務メモ(追記のみ)
    ├── tasks.json       タスク一覧
    ├── files/           成果物(社員が読み書きできる唯一の領域)
    └── sessions/        日付ごとの会話ログ
```

置き場所は `--office` または環境変数 `AI_EMPLOYEE_HOME` で変更できます。
案件台帳は読み込み→更新→書き戻しの単純な方式なので、複数の社員を同時並行で走らせる場合は
同じ案件への同時更新を避けてください。

## Python から使う

```python
from ai_employee import Employee, Workspace

ws = Workspace("eigyo")
employee = Employee(ws.load_profile(), ws)

result = employee.work("今週フォローすべき案件を、優先順位をつけて出して")
print(result.text)
print(result.tool_calls)   # 実際に使ったツール
print(result.ok)           # 拒否・打ち切りがなければ True

# 案件台帳には直接アクセスもできる
for pj in employee.ledger.list(stage="実施設計"):
    print(pj["name"], pj["next_action"])
```

`Listener` を継承して `Employee(..., listener=...)` に渡すと、
本文・思考・ツール呼び出しをストリーミングで受け取れます(CLI の画面表示もこれを使っています)。

## 設計上の判断

- **エージェントループは手書き**。ツール実行の途中経過をトークン単位で表示したいこと、
  ベータ依存(Tool Runner)を避けたいことから、`client.beta.messages.stream` を使った
  手動ループにしています。並列ツール呼び出しの結果は 1 つの user メッセージにまとめて返します。
- **プロンプトキャッシュ**。system は「職務定義書(不変)→ 現在時刻・未完了タスク・担当案件(揮発)」の
  順に組み立て、不変部分の末尾だけにキャッシュ区切りを置いています。案件が動いても
  職務定義書側のキャッシュは効き続けます。ツールの並び順も指定順に依存しないよう定義順に固定。
- **拒否時のフォールバック**。Opus 5 は安全性判定で `stop_reason: "refusal"` を返すことがあるため、
  サーバ側フォールバック(`fallbacks: "default"`)を既定で有効にしています。
  それでも拒否された場合は例外にせず `TurnResult.refusal` として返します。
- **暴走の抑制**。ツール呼び出しは 1 依頼あたり 24 回、`pause_turn` からの再開は 5 回で打ち切ります。
- **社員は落ちない**。ツールの失敗は例外にせず `is_error` 付きの結果としてモデルに返し、
  社員自身に回復させます。
